# 릴리스 워크플로

## 첫 릴리스 {/* #first-release */}

버전 패턴에 일치하는 태그가 없으면 첫 버전을 직접 지정하세요.

```bash
flopha next-version --initial-version 0.2.0 --pattern 'mobile@{semver}' --create --push
# Creates mobile@0.2.0 and pushes it to origin
```

첫 버전은 `MAJOR.MINOR.PATCH` 형식으로 지정하세요. 접두사, 접미사, 빌드 메타데이터를 넣거나 숫자 앞에 0을 붙이면 안 됩니다. 세 숫자는 각각 부호 없는 32비트 정수 범위 안에 있어야 합니다. 태그 이름은 패턴으로 정하며, 패턴에는 세 자리 표시자를 모두 넣거나 `{semver}`를 사용해야 합니다. 브랜치 패턴이 `release/{semver}`인 경우처럼 `--source branch`를 사용할 때도 `--initial-version`을 지정할 수 있습니다.

설정 파일로 릴리스를 실행할 때는 `[version]` 아래에 첫 버전을 적으세요.

```toml
[version]
pattern = "mobile@{semver}"
initial_version = "0.2.0"

[[manifest]]
path = "package.json"
type = "npm"
```

```bash
flopha release --dry-run       # preview mobile@0.2.0 without writing files
flopha release --prepare       # update manifests to 0.2.0 for review
# After committing the prepared files:
flopha release --require-version-match --dry-run
```

설정 파일에 적은 첫 버전 대신 다른 값을 사용하려면 `release --initial-version 0.3.0`처럼 실행하세요. 첫 버전은 `auto = true`나 버전 증가 옵션을 지정해도 값이 올라가지 않고 그대로 사용됩니다. 패턴에 맞는 정식 태그가 생긴 뒤에는 일반적인 버전 증가 규칙이 적용되므로 초기 버전 설정을 지울 필요는 없습니다. 일치하는 버전도 없고 초기 버전도 지정하지 않으면 두 명령 모두 지정 방법을 안내하며 실패합니다. 첫 릴리스의 변경 내역에는 HEAD에서 도달할 수 있는 모든 커밋이 포함됩니다.

첫 버전을 사전 릴리스로 만들려면 `next-version`에 `--pre beta`를 추가하거나 `[version]`에 `pre = "beta"`를 설정하세요. 태그는 `mobile@0.2.0-beta.1`, 매니페스트의 버전은 `0.2.0-beta.1`이 됩니다. 사전 릴리스 태그가 이미 있다면 해당 채널의 번호가 올라갑니다. 같은 버전의 사전 릴리스를 이어서 만들 때는 초기 버전을 바꾸지 마세요. 채널을 생략하면 첫 정식 태그인 `mobile@0.2.0`을 만듭니다.

## 커밋 메시지 규약 {/* #conventional-commits */}

최신 버전 이후의 커밋 메시지로 다음 버전 증가 수준을 판단하려면 `--auto`를 사용하세요.

```bash
flopha next-version --auto
```

내장 규칙은 다음과 같습니다.

- `BREAKING CHANGE` 또는 `feat!:` 형식의 커밋은 메이저 버전을 올립니다.
- `feat:` 형식의 커밋은 마이너 버전을 올립니다.
- 그 외 커밋 내역은 패치 버전을 올립니다.

## 사용자 지정 버전 증가 규칙 {/* #custom-bump-rules */}

팀에서 다른 커밋 규칙을 사용한다면 `--rule`로 내장 규칙을 대체하세요.

```bash
flopha next-version \
  --auto \
  --rule 'major:BREAKING CHANGE' \
  --rule 'minor:^feature'
```

각 규칙은 `level:regex` 형식이며 `level`에는 `major`, `minor`, `patch` 중 하나를 지정합니다.

## 브랜치 기반 릴리스 흐름 {/* #branch-based-release-streams */}

태그 대신 브랜치에서 릴리스를 게시하는 팀도 있습니다. 이 경우 `--source branch`를 일관되게 사용하세요.

```bash
flopha last-version --source branch --pattern "release/{major}.{minor}.{patch}"
flopha next-version --source branch --pattern "release/{major}.{minor}.{patch}"
flopha next-version --source branch --pattern "release/{major}.{minor}.{patch}" --create
```

## 릴리스 이력 확인 {/* #auditing-release-history */}

이미 게시된 릴리스를 확인하려면 `log`를 사용하세요.

```bash
flopha log --pattern "desktop@{semver}" --limit 20
```

로그에는 버전과 릴리스 날짜, 패턴에 맞는 이전 버전 이후에 쌓인 커밋 수가 표시됩니다.

## CI에서 flopha 사용하기 {/* #using-flopha-in-ci */}

모든 flopha 명령은 기본적으로 일반 텍스트를 출력합니다. 스크립트에서 결과를 처리할 때는 `--format json`을 사용할 수 있어 어떤 CI 파이프라인에도 쉽게 연결할 수 있습니다.

### 최소 릴리스 파이프라인(셸) {/* #minimal-release-pipeline-shell */}

```bash
# 1. Compute the next version without creating it yet
NEXT=$(flopha next-version --auto --format json | jq -r '.version')

# 2. Generate changelog headed with the upcoming version
flopha changelog --title "Changes in $NEXT" --output CHANGELOG.md

# 3. Commit the updated changelog
git add CHANGELOG.md
git commit -m "chore: release $NEXT"

# 4. Tag and push
flopha next-version --auto --create
git push origin "$NEXT"
```

`--title`은 태그가 생성되기 전에 다음 버전을 변경 내역 제목에 넣습니다. 기존 태그 또는 참조까지로 변경 내역 범위를 제한할 때만 `--to`를 사용하세요.

### GitHub Actions — 액션 사용 {/* #github-actions--using-the-action */}

`sjquant/flopha` 액션은 일반적인 태그 생성 및 릴리스 흐름을 단계 하나로 제공합니다.

```yaml
name: Release

on:
  push:
    branches: [main]

permissions:
  contents: write

jobs:
  release:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0        # full history so flopha can walk commits

      - name: Tag and release
        uses: sjquant/flopha@v1
        with:
          auto: true
          create-release: true
          changelog: true       # generate changelog and use it as the release body
```

### GitHub Actions — 전체 변경 내역 파이프라인 {/* #github-actions--full-changelog-pipeline */}

태그 생성 전에 변경 내역을 직접 제어하려면 다음과 같이 구성하세요.

```yaml
name: Release

on:
  push:
    branches: [main]

permissions:
  contents: write

jobs:
  release:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0

      - name: Install flopha
        run: |
          curl -fsSL https://raw.githubusercontent.com/sjquant/flopha/main/scripts/install.sh | sh
          echo "$HOME/.flopha/bin" >> $GITHUB_PATH

      - name: Compute next version
        id: version
        run: echo "tag=$(flopha next-version --auto --format json | jq -r '.version')" >> $GITHUB_OUTPUT

      - name: Generate changelog
        run: flopha changelog --title "Changes in ${{ steps.version.outputs.tag }}" --output CHANGELOG.md

      - name: Commit changelog
        run: |
          git config user.name  "github-actions[bot]"
          git config user.email "github-actions[bot]@users.noreply.github.com"
          git add CHANGELOG.md
          git diff --staged --quiet || git commit -m "chore: release ${{ steps.version.outputs.tag }}"
          git push

      - name: Create tag and release
        uses: sjquant/flopha@v1
        with:
          auto: true
          create-release: true
```

### 릴리스 PR 준비 {/* #prepare-a-release-pr */}

버전 변경 사항을 PR에서 검토하려면 파일을 수정하는 단계와 릴리스를 게시하는 단계를 나누세요.

```bash
flopha release --prepare
# Review and commit the modified manifests, then open a PR.
flopha release --require-version-match --dry-run   # validate the PR without publishing
flopha release --require-version-match             # publish after merge
```

`--prepare`는 `flopha.toml`의 규칙에 따라 매니페스트를 수정합니다. 로컬 Cargo 패키지에 해당하는 잠금 파일 항목도 함께 갱신합니다. 수정한 파일은 스테이징하지 않은 상태로 남겨 둡니다. 커밋하거나 태그를 만들거나 푸시하지 않으며, GitHub 릴리스도 만들지 않습니다. 파일을 기록하지 않고 작업 내용만 확인하려면 `--prepare --dry-run`을 사용하세요. 준비와 검증 모두 매니페스트 대상이 하나 이상 설정되어 있어야 합니다.

`--require-version-match`는 매니페스트 중 하나라도 계산된 버전과 다르면 실패합니다. 모두 일치하면 버전 변경 커밋을 새로 만들지 않고 이미 커밋된 버전을 릴리스합니다. CI에서 detached HEAD 상태로 체크아웃한 경우에도 사용할 수 있습니다. 인증 정보 없이 게시하지 않고 PR만 검증하려면 `--dry-run`을 추가하세요. `--prepare`와 `--require-version-match`는 함께 사용할 수 없습니다.

준비 후 새 커밋으로 필요한 버전 증가 수준이 달라졌다면 기준 브랜치의 변경 사항을 버전 브랜치에 반영하고 `--prepare`를 다시 실행한 뒤 수정된 버전을 커밋하세요. 버전 PR이 이미 머지되었다면 후속 PR을 만드세요. 버전 PR 자체가 메이저 또는 마이너 버전 증가를 유발하지 않도록 중립적인 커밋 메시지를 사용하세요.

이 저장소도 이 흐름을 따릅니다. 버전 PR에서 `Cargo.toml`과 `Cargo.lock`을 변경하며, 머지 시 해당 Cargo 버전이 아직 게시되지 않은 경우에만 초안 릴리스를 시작합니다. 기존 빌드 작업은 게시 전에 해당 태그를 빌드하고 바이너리를 업로드합니다. 초안은 생성되었으나 빌드나 업로드가 실패했다면 처음 실패한 워크플로를 다시 실행하세요.

### GitHub Actions에서 `flopha release` 사용 {/* #flopha-release-in-github-actions */}

저장소에 `flopha.toml`을 커밋해 두면 `flopha release` 한 번으로 버전을 올리고, 매니페스트를 맞추고, 태그와 변경 내역, GitHub 릴리스를 만들 수 있습니다. 매번 푸시할 때 실행하거나 같은 작업을 다시 실행해도 안전합니다. 새 커밋이 없으면 아무 작업도 하지 않습니다. 이미 태그가 있는 커밋에서는 앞선 실행에서 끝내지 못한 태그 푸시와 GitHub 릴리스 생성만 마무리합니다.

```yaml
name: Release

on:
  push:
    branches: [main]

concurrency: release        # back-to-back pushes would race for the same tag

permissions:
  contents: write

jobs:
  release:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0    # full history and tags to detect the bump

      - name: Install flopha
        run: |
          curl -fsSL https://raw.githubusercontent.com/sjquant/flopha/main/scripts/install.sh | sh
          echo "$HOME/.flopha/bin" >> $GITHUB_PATH

      - name: Release
        run: |
          git config user.name  "github-actions[bot]"
          git config user.email "github-actions[bot]@users.noreply.github.com"
          flopha release
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}   # used to create the GitHub Release
```

- 기본 `GITHUB_TOKEN`으로 푸시하면 새 워크플로 실행이 시작되지 않으므로 버전 증가 커밋이 또 다른 릴리스를 시작하지 않습니다.
- `main`에 풀 리퀘스트가 필수라면 `[[manifest]]` 대상의 버전 증가 커밋은 거부됩니다. 워크플로 토큰이 해당 규칙을 우회하도록 허용하거나, `[[manifest]]`를 제거해 `release`가 태그만 푸시하도록 하세요.
- `[[manifest]]` 대상이 있으면 HEAD는 분리된 상태가 아니라 브랜치를 가리켜야 합니다. `push` 이벤트에서는 `actions/checkout`이 이를 처리합니다. `pull_request` 이벤트나 SHA 체크아웃에서는 먼저 `git checkout -B <branch>`를 실행하세요.

### JSON 출력으로 스크립트 작성 {/* #scripting-with-json-output */}

모든 명령은 `--format json`을 지원하므로 안전하게 `jq`로 파싱할 수 있습니다.

```bash
# Extract version string
flopha next-version --auto --format json | jq -r '.version'

# List recent releases as JSON array
flopha log --limit 5 --format json

# Generate changelog as structured data for a historical range
flopha changelog --from "v1.9.0" --to "v2.0.0" --format json | jq '.groups[].title'
```

### 재사용 가능한 릴리스 스크립트 {/* #reusable-release-script */}

다음 스크립트는 다른 파일 없이 어떤 CI 환경에서도 사용할 수 있습니다.

```bash
#!/usr/bin/env bash
set -euo pipefail

NEXT=$(flopha next-version --auto --format json | jq -r '.version')
echo "Releasing $NEXT"

flopha changelog --title "Changes in $NEXT" --output CHANGELOG.md
git add CHANGELOG.md
git diff --staged --quiet || git commit -m "chore: release $NEXT"
git push

flopha next-version --auto --create
git push origin "$NEXT"
```
